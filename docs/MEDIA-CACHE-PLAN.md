# 音频与 MOV 预览：以原始证据驱动的优化方案

日期：2026-11-14（America/Denver）。状态：已授权执行，本机 0.7.77 修复与应用重开验收通过；整机重启未测。详见 [实测结果](MEDIA-CACHE-RESULTS-20261114.md)。下文保留实施前的方案与验收定义。
本文件是该主题唯一方案；当前项目现状与执行日志仍在 [HANDOFF](HANDOFF.md)。

## 目标与已有证据

目标：打开素材目录时尽快可操作；同一源版本、同一预览规则、有有效产物时不重复生成；播放内容正确。
前轮只验证了局部复用机制与重导入缺陷，未取得用户现场完整时间线，不能把该缺陷写成所有卡顿的原因。
既有证据：`work/media-cache-audit-20261114/report.json`。不为修订方案重复跑已经通过且未变化的用例。

## 1. 从什么原始材料入手

1. 从发生问题的实际安装程序、真实文件副本与实际打开动作开始；记录程序/ASAR 摘要、用户数据目录、存储位置及样本摘要。
2. 先测一个确实慢的目录、一个反复提示的 MOV；再加一个正常对照。合成样本用于稳定回归，不能替代现场复现。
3. 查媒体内部流：编码、像素格式、位深、透明、尺寸、时长、音轨；MOV 扩展名与封面都不能证明实际播放能力。
4. 记录点击目录→索引返回→首批可交互→请求波形→解码/转码→实际播放。记录等待、执行、文件读取与界面绘制的分段耗时。
5. 区分无派生产物、仅应用重开、操作系统冷文件缓存三种状态；完整重启应用与数据库重开分别记录。整机重启单独安排，不以任何其他测试替代。

## 2. 先写能被推翻的解释

| 暂定解释 | 能支持或推翻它的观察 |
| --- | --- |
| 屏幕外音频提前工作挤占资源 | 同一输入只延后屏幕外波形/媒体预读，比较首屏交互、源文件读取和解码任务数；没有改善就不称为主因 |
| MOV 预览关联丢失导致重算 | 对齐同一源版本的数据库路径、旧产物和新转换命令；已有孤立复现，仍需匹配现场动作 |
| 缓存淘汰造成往返重算 | 必须找到先发生的淘汰记录、配额原因和后续 miss；无证据不以扩大容量作主修复 |
| 提示或界面卡顿发生时没有转换 | 若转换次数为 0，转查原生解码、IPC、索引查询和绘制时间；文字提示不能作转换回执 |

每次对照只改变一个变量；固定输入、程序版本、窗口与滚动位置，冷态和热态分开。
一次短追踪先定位主耗时；只改阻断主流程的环节。不存在支持证据的方向不提前改架构或加功能。

## 3. 具体工具、用途与限制

| 工具/方法 | 具体用途 | 当前状态/边界 |
| --- | --- | --- |
| ffprobe + FFmpeg | `ffprobe -v error -show_format -show_streams -of json sample.mov` 查媒体流；独立完整解码派生产物检查错误/截断 | ffprobe 9.0.1 已在 PATH；运行时另记转换器实际版本。探测或完整解码通过仍不等于一幕播放器通过 |
| Windows WPR/WPA；必要时 Process Monitor | 对齐应用/转换子进程 CPU、磁盘/File I/O；Procmon 查进程创建、原文件/缓存读写与失败路径 | wpr.exe 已存在；WPA/Procmon 安装与采集权限尚未确认。只捕获目标进程的短窗口，先选一套系统追踪 |
| Electron contentTracing + Perfetto | 查 Chromium 主线程长任务、媒体解码与绘制；与应用 request ID/单调时钟事件对齐 | 本项目 Electron 45；官方当前格式为 Perfetto protobuf，不假设旧 JSON。未开始采集 |
| 独立 Node 验证程序 + Playwright 驱动实际 EXE | 只读核对文件摘要、SQLite 关联与转换次数；执行真实滚动、点击、播放、退出重开 | 复用既有隔离启动方法；只断言缓存 API 返回成功不足以验收 |

诊断事件最小字段：run/request ID、源版本、产物类型、cache hit/miss 及原因、排队/执行起止、转换子进程与产物状态。
原因必须区分 absent、source_changed、recipe_changed、evicted、corrupt、offline、permission_error；后两项不能当成“缺缓存”无限重试。
窗口为有边界的一段操作，记录结束后释放采集；不常驻记录所有文件活动。追踪损失事件时不得据“没看到”证明零转换。

## 4. 修订后的实现顺序

### A. 先建立因果证据与验收基线

取得一个真实慢场景的时间线；记录首屏可交互、首次可播放、CPU 时间、读取字节、解码/转码数与排队长度。
采样次数在修改前固定；样本少报告原始值、中位数/最大值，不包装为可靠 P95。基于实测和用户操作需求，在编码前写定耗时门槛。
若找不到额外转换，不沿“转码重复”继续改；先处理追踪指向的主线程或读取问题。

### B. 把预览作为可复用的派生产物维护

保留当前有效预览关联；重新导入不变文件不得覆盖。请求生成前先查询有效产物，不依赖前端曾经记住结果。
登记拆为两层：源文件/版本记录，以及该源版本按特定规则生成的产物。请求键由源版本、产物类型、实际转换规则及相关工具版本构成。
路径用于定位文件，不独自代表内容；标签、排序或无关软件版本变化不使媒体预览失效。不同分辨率、透明策略等转换规则须区分。
复用已有摘要和文件身份信息；新增/疑似变更文件在后台核验。不能在每次开机全量哈希数万文件，把重复解码换成重复读盘。
大小与 mtime 相同不保证字节相同；外部程序保留这些属性覆盖文件时，需要内容复核才能给严格保证。首次计算摘要也属于资源预算。

产物完成并通过必要校验后才发布文件、提交索引；临时文件与已完成结果分开。进程中断后不能把半成品视作命中。
文件发布和 SQLite 提交不能假装是同一原子事务；在两者之间退出时，可凭确定的产物键发现并校验旧产物，补回关联。
同键多个请求只执行一次、共享结果；一个窗口关闭不应误杀仍被另一窗口使用的任务。源文件在转换期间变化则不发布旧版本结果。
旧预览按需接管、保留现成可用结果；不能为了升级方案全库重新生成。无法验证旧产物的身份时明确标注，不能伪称已校验。

### C. 音频只做当下需要的工作

先从索引显示名称和已有时长，列表交互不等待全文件解码。可视范围内按需读取已有波形；无缓存才排队生成。
真正试听时再设置媒体源/加载音频；不能仅设 preload=none 却继续显式 load 或提前请求解码。
显式播放优先于可见波形；切目录丢弃无人需要且未开始的任务。并发与批量按测得的 CPU/I/O 调整，不默认提高进程数。
重绘保留仍有效的播放器/波形结果，避免每次列表更新都重新读媒体头。

### D. 仅在证据支持时调整淘汰

当前播放或转换正在使用的产物不能淘汰；淘汰必须留下原因，缺失后可重建，离线或权限错误不可误删有效预览。
先用工作集与产物大小检查现有 200 项/2 GiB 是否引发往返失效，再决定容量和保留策略；不把更大的缓存当作性能诊断。
界面区分“读取已有预览”“等待生成”“正在生成”“源文件离线”。提示由实际状态驱动。

## 5. 三项必要验收，以及第三方如何复核

| 验收项 | 必须满足的规则 | 独立证据 |
| --- | --- | --- |
| 复用且不显示旧内容 | 源、规则与有效产物均未变化时，退出重开/重复导入/往返目录新增生成次数为 0；源或规则变化只生成所需的新产物；取消/中断不留下可命中的半成品 | 固定输入、程序摘要、SQLite 前后快照、产物摘要、带完整性说明的系统追踪；原文件摘要不变。整机重启另记实测状态 |
| 加载更轻且可操作 | 未进入可视区且未被播放请求的音频不新建波形/预读音频；首屏交互不等待波形；达到修改前固定的耗时门槛，且不靠把所有工作推迟到首次试听来掩盖问题 | 同输入、同机器和预定采样次数的前后时间线、读取量、CPU 时间；同时报告首次试听与热打开 |
| 产物内容与实际播放正确 | 一幕实际 EXE 中开头/中间/结尾播放及跳播通过；时长/音轨符合预览契约；透明样本对照已知 alpha 图案；静音/瞬态信号波形无错位；原件不变 | 独立解码检查 + 已知真值样本 + 实际 Chromium 消费端。哈希只能证明字节未变，不能代替可播放与画面正确 |

证据包：每个日期/run ID 保存样本清单与摘要、版本/启动配置、系统/Chromium 原始追踪、命令和退出码、数据库快照、验证脚本和报告。
独立验证程序直接读文件与数据库、驱动实际程序，不调用被测“命中成功”接口充当裁判。旧版应复现缺陷，新版应通过同一输入与判定。
另一位维护者能据同包复跑并推翻结论；第二台 Windows 机器只验证迁移边界，不能代替用户本机耗时与播放体验。分享前使用可分发或脱敏副本。
本轮没有运行上述新增验收；既有局部通过与待验证现场保持区分。下一步首先完成 A，再按测量结果实施最小修改。

## 方法依据

- [FFmpeg：ffprobe](https://ffmpeg.org/ffprobe.html)：查看真实容器和媒体流，输出机器可读信息。
- [Microsoft：WPR](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/introduction-to-wpr) 与 [Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon)：系统资源与文件/进程活动证据。
- [Electron：contentTracing](https://www.electronjs.org/docs/latest/api/content-tracing)：Chromium 性能追踪与 Perfetto 输出。
- [Bazel：Remote Caching](https://bazel.build/remote/caching)：输入/动作到结果元数据及产物存储的分层；也列明输入并发变化和工具身份造成错误复用的边界。这里据此提出本地派生产物设计建议，不宣称官方已验证一幕方案。
