# 逆向对齐开发的消耗复盘与执行规则

日期：2026-10-22。对象：YimuCraft。作者：Codex。用户明确要求复盘并固化，供以后类似任务提前识别和采用。

## 结论与责任

主要问题不是用户要求 1:1，也不是“测试太认真”，而是我没有足够早地把用户关键流程变成可重复的验收用例；实现面扩张、测试环境不稳、失败试探和频繁构建叠加，产生了大量重复工作。用户不断要求继续，不应被解释成无限重试同一方法或不断扩展旁支。

这份复盘固化的是执行约束；“实施这些规则后能节省多少 Token”尚未经后续项目验证，不虚构收益。

## 1. 证据与统计边界

- 本地盘点见 evidence/token-retrospective-20261022.json：36 个版本目录、103 个 scripts 文件；native-card-drag 前缀 10 个夹具目录、native-drag 9 个、ole 前缀 17 个、pr-collect-ui 10 个。前缀可能有包含关系，不相加成总尝试数。
- 目录数不是执行次数，不等于无效次数；版本目录也不等于每个版本都安装过。它们仅证明迭代面和维护负担较大。
- 最新拖放回执失败、历史通过被覆盖、安装后源码变化、文档版本冲突，均可从 HANDOFF 和 handoff-20261022 快照核对。
- 未取得可靠的全程分环节 Token 账单；不能给出各环节占比、确切浪费量或承诺节省百分比。此次未继续深挖大量会话日志，以免复盘本身变成另一轮无边界消耗。
- 宿主启动、构建、等待主要消耗墙钟时间；反复推理、工具请求/输出、长上下文恢复才直接增加模型用量。二者不能混为一个指标，缓存与实际计费另有区别。

## 2. 哪些环节最值得纠正

以下按整改优先级排列，不是 Token 账单排名。

| 环节 | 已观察行为 | 浪费机制 | 以后如何提前阻断 |
|---|---|---|---|
| 关键流程验收过晚 | 用户多次指出 LUT 不生效、音频默认行为、右键和界面不对；后来才补真实像素、完整卡片鼠标链路 | “代码有功能”被当成足够接近，导致改完再返工 | 开工先用同输入、同动作、同输出定义最重要的 3–5 条流程，先贯通一条再扩大 |
| 同一问题连续猜测 | 拖放尝试延迟、调试轮询、接收窗口位置；最终仍有窗口命中失败 | 产品、输入工具、DPI、焦点和调试阻塞混在一起，每次只改猜测参数 | 同假设无新增证据失败两次就换诊断；第三次前必须有可区分原因的观测 |
| 宿主环境未先校准 | PR 直接启动扩展失败；CEP reload 后旧 Node 定时器仍运行 | 在旧代码或异常启动环境里测试新代码，失败信息误导定位 | 先证明当前加载版本、心跳、活动工程和一个最小往返；不可靠则先修环境 |
| 频繁构建和安装 | 留下大量版本目录，0.7.23–0.7.27 多轮安装记录 | 单个小改动重复打包/启动/安装/核对；又与未安装源码混淆 | 源码定向测试先行；按用户流程合并稳定改动，遇安装路径/依赖/桥接风险才提前安装 |
| 优先级漂移 | 卡片拖放尚未闭环时继续推进 OBJ/MTL 等格式 | 新能力有价值，但不能替代最高优先级缺口的解决；切换上下文也有成本 | 只设一个主攻缺口；确实受阻才推进独立次项，并写清阻塞证据与返回条件 |
| 证据和状态未形成稳定资产 | 固定名 JSON 覆盖历史；README/主档/状态页各写不同版本；没有 Git 提交 | 下次要重新确认“当时测了谁、现在是哪版”，甚至重跑已验证步骤 | 单一现状主档、运行 ID、源码/安装哈希、保留失败；建立干净提交基线 |
| 工具输出与上下文膨胀 | 大段源码/多文件输出截断，超长汇总、读后重读；交接 patch 失败后重写 | 大量无关内容进入上下文；截断导致补读，长输出再被总结 | 先 rg 定位再读小段；长日志存文件只提取结论和首个错误；编辑失败先修调用方式 |
| 夹具和脚本增殖 | 多批类似夹具和 103 个脚本；规模测试曾用不足以代表真实解码的样本 | 每次重建环境、复制代码，测试自身维护量膨胀；假样本需重做 | 复用少量已校准夹具和参数化脚本；只在隔离/破坏性验证需要时新建副本 |
| 原版观察与推断混用风险 | 静态接口、历史功能、实机入口、当前行为不在同一证据层 | 按“猜测应该存在”的功能开发，最后仍需重查对照 | 每个待办先标观察方式；只做解决当前不确定性的定向分析，不穷举整个程序 |

## 3. 必须保留的投入

真实 LUT 像素验证发现参数存储不等于实际加载；PR 静默重开发现自动寻址掩盖旧路径；源目录离线发现迁移依赖问题。这些检查揭露了真实缺陷，不能为了省 Token 删掉。

合理优化是把这些检查前置、复用，避免每次重新制作夹具。不要把减少测试、取消重启/离线验证、隐藏失败或降低 1:1 目标当成效率提升。

## 4. 下次我必须自主执行的预判流程

### 开工前：用最少信息识别高风险

读取项目规则和主档，提取 3–5 个关键词，只查最相关 1–3 条经验。列出关键流程、最不确定边界、最小样本和成功判据，不编写庞大方案。

出现桌面宿主、原生拖放、文件迁移、专有包、长任务时，默认视为集成风险：先做最小端到端验证。遇到“1:1”先核对行为，不能用通用素材管理器经验替代原版观察。

### 每次实验前：四个问题

1. 当前假设是什么？属于产品、环境、测试工具还是原版行为问题？
2. 最便宜的哪个观测能区分它和其他原因？
3. 本次只改变什么变量，什么保持不变？
4. 成功/失败后下一步是什么，是否会获得新信息？

写在当前日志的短条目里即可，不另建庞大流程系统。无法回答第 4 项，不运行同样实验。

### 重试与转向门槛

- 同一假设连续两次失败且无新增证据，禁止第三次只调延迟、坐标、重启或重跑；先缩小复现、加观测或更换方法。
- 单个缺口约 20 分钟仍没有减少不确定性，做一次方向检查；这是内部判断点，不是停止用户任务或再次索要开工许可。
- 仍受阻则记录已排除原因、当前证据、恢复条件，推进独立任务；不要把未证实假设升级为结论。
- 环境出现旧脚本、心跳失效、错误宿主/窗口、原版样本不可用，先停止相关功能测试，校准环境；不得绕过保护。

以上时间和次数是默认工作约束，不是经实验证实的最佳阈值。新证据足以支持继续时可调整，但必须写明理由。

### 构建与测试门槛

改动→最相关测试→用户流程回归→必要安装验证。通过后仅在新改动、失败或未解决风险出现时扩大/重复测试。不要每改一处就全套回归、发布一个版本。

涉及安装资源路径、原生依赖、CEP 部署等，安装验证本身是必要条件，可提前执行。普通 UI 文案和可逆低影响改动不增设镜像实现的测试。

### 上下文与调用控制

默认一次工具输出控制在约 1–3 千 Token，确有必要才增大；先定位后读，不同时倾倒多份长文件。独立只读查询合并，依赖操作顺序执行。日志输出首错、摘要、文件位置，其余落盘。

接续只读当前状态、最近增量和本次相关模块；不重复加载全部历史。长日志保留在文件，主档当前摘要保持短，历史按章节定位。日志要求不能演变成每个工具调用都写长篇复述。

## 5. 可复用经验卡（用户授权固化，效果待后续验证）

### 卡 A：先校准宿主，再修业务
- 行动：核对实际脚本版本、心跳、活动工程和最小请求回执。
- 结果：本项目查出 PR 启动环境及 CEP 旧轮询干扰，避免继续把环境错当业务错。
- 原因：代码变更未必进入正在执行的宿主上下文。
- 验收：目标版本/请求 ID 对应，最小操作真实生效，再运行功能测试。
- 反例：重载页面后假定 Node 定时器已消失；不断改业务代码。
- 边界：本机 PR/CEP 观察可复用为检查方向，不能外推所有宿主故障根因。

### 卡 B：迁移和渲染看最终结果
- 行动：源与中间库离线，宿主重开；LUT 对照实际导出像素。
- 结果：发现旧路径和参数假成功，形成真正能暴露缺陷的测试。
- 原因：自动寻址、缓存和参数回读会掩盖不可迁移或未生效。
- 验收：目标依赖可定位、零缺失、内容/像素正确、原用户工程不受损。
- 反例：只比较文件存在或 API 返回成功。
- 边界：样本通过只覆盖该格式/宿主/构建，不代表完整兼容。

### 卡 C：失败要增加信息，不能只增加尝试次数
- 行动：同假设两次无新增证据后转为分层诊断，保留每次输入/版本/错误。
- 结果：本次固化规则；尚无后续节省 Token 的验证数据。
- 原因：测试工具失败与产品失败混合，重复参数试探难以收敛。
- 验收：下一次实验能明确排除或支持一个原因；重复阶段可解释为何必要。
- 反例：延迟从 100 改 200、反复启动，却没有可区分原因的观测。
- 边界：有新证据的合理重试不受机械次数限制；不能用上限逃避任务。

## 6. 以后如何检查规则是否有效

已有日志增加两个简短字段即可：本轮新增证据、未重复运行的理由。必要时记录有效实验/无信息重试、安装次数、重复读取和用户重新纠正次数，不引入新的统计系统。

后续有可用模型用量数据时再比较同类任务成本；没有数据只报告可观察的返工减少。仍保持真实验收标准。项目开发当前暂停，本次仅更新复盘和规则。
